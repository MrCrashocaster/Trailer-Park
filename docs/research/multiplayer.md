# Original multiplayer design notebook

Status: proposals only. The user has approved neither an engine nor a specific game format.

## Working hypothesis

A small cooperative neighborhood sandbox could make plans, improvisation, and escalating consequences playable. Begin by evaluating 2–4 players for a prototype; this is a scope suggestion, not a requirement. A larger persistent server would require a different production and moderation plan.

A candidate loop: identify a household need → gather resources and favors → divide work → execute a hustle → respond to complications → settle debts and relationships. Failure should create a playable recovery opportunity.

## System proposals

| Original system | Player interaction | Prototype question |
| --- | --- | --- |
| Repair-and-resale business | One player diagnoses, another sources parts, another negotiates | Do different tasks remain useful and fun? |
| Community event contract | Players arrange power, equipment, supplies, and attendance | Can a complication create a new plan without erasing all progress? |
| Favor ledger | Players trade access, labor, and borrowed equipment with residents | Are obligations understandable without excessive menus? |
| Neighborhood attention | Witnesses react to noise, damaged property, and missed promises | Can players predict consequences from visible evidence? |
| Shared equipment | A limited cart, trailer, or generator forces coordination | Does scarcity create cooperation or merely waiting? |
| Conflicting NPC priorities | Residents offer incompatible requests | Can players negotiate tradeoffs without mandatory betrayal? |
| Optional interview moments | Players explain the session's events in their own words | Is this enjoyable after the first session? Avoid mandatory recording. |

These activities and examples are original design proposals, not claims about specific episodes.

## Small candidate vertical slice

One compact original neighborhood, one cooperative repair business, three residents with conflicting needs, a handful of interactable props, and a single event with several recoverable complications. Demonstrate: join session, share a task, move an object, complete a transaction, observe a consequence, and reconnect.

This is a discussion baseline. Perspective, movement, art style, platform, and player count should be decided before implementation.

## Multiplayer engineering questions

- Who hosts: a player, a dedicated server, or both? What happens when the host leaves?
- Which actions need server authority: money, ownership, inventory, contracts, and persistent changes?
- How are object grabs, dropped items, simultaneous purchases, and NPC interactions resolved?
- What persists per player, household, and session? How do saves handle disconnects and duplicated transactions?
- What cooperation survives ordinary latency? Avoid making basic progress depend on perfectly synchronized physics.
- How do permissions protect shared money and property from griefing? Consider private sessions and explicit access controls first.
- Is voice chat required, optional, or absent? Choose text/ping alternatives and recording policy deliberately.

These are design requirements to resolve, not evidence that any networking implementation exists.
